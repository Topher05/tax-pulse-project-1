FEDSTACK CAPSTONE PROJECTS
Multi-tenant SaaS products with case management, a multi-step workflow,
and an internal staff + external portal split.
═══════════════════════════════════════════════════════════════════════════════

Each capstone is framed as an enterprise product sold to a specific buyer (a
tax-prep firm, a wealth-advisory firm, a corporate finance team, or a
payroll/HR service provider). Each app is built around a Case entity that
moves through a defined multi-step workflow with assigned owners and an
immutable audit trail.

Three foundational concepts apply to all four products:

  1. CASE MANAGEMENT — Every unit of work is represented as a Case (a Tax
     Engagement, a Tax Plan Cycle, an Expense Report, or a Nexus Filing).
     Each Case has a unique ID, a current stage, an assigned owner, a due
     date, a priority, an `on_hold` pause flag, attached artifacts, comments,
     and a complete audit trail. (Condition lives in the stage — there is no
     separate status field; see each product's stage table.)

  2. MULTI-STEP WORKFLOW — Cases move through named stages. Stage
     transitions require the actor's role to be authorized; some transitions
     require a second-pair review (modeled as a normal role-gated transition
     with REVIEW permission — not a separate subsystem). The workflow engine
     enforces sequence and records denied attempts.

  3. INTERNAL vs EXTERNAL ROLES — Internal users are employees of the firm
     that bought the product (the tenant). External users are the firm's
     customers, employees, or counterparties — they sign in to a portal
     scoped to their own data. Every app additionally has a platform Admin
     for the vendor selling the SaaS.

Permission levels used in the matrices:

  FULL    — view + create + edit + delete + administer
  EDIT    — view + create + edit (own records or assigned cases)
  REVIEW  — view + approve / reject / send back; can advance stage
  VIEW    — read-only access
  SCOPED  — access limited to records explicitly granted/assigned
  —       — no access (feature hidden from this role's UI)

TaxPulse Advisory — Tax Liability Planning for Wealth Advisory Firms
═══════════════════════════════════════════════════════════════════════════════

Target buyer:
  Independent RIAs (Independent Registered Investment Advisors), multi-family 
  offices, and wealth-management firms with 100–2,000 high-net-worth clients. Tax 
  planning is one of their highest-value services and the biggest source of 
  analyst hours.

Business case:
  Most wealth firms run tax planning in spreadsheets that don't survive staff
  turnover and aren't auditable to the client. TaxPulse turns planning into a
  versioned, reviewable Plan Cycle — every scenario is captured, every advisor
  recommendation is logged, every action a client agreed to is tracked.

Case entity:
  Tax Plan Cycle — one Case per (client × planning period, typically
  quarterly). Carries the client's income/deduction picture, the modeled
  scenarios, the chosen recommendation, and the action checklist.

Workflow stages (7):
  ┌─────────────────┬──────────────────────────────────────────────────────┐
  │ Stage           │ What happens                                          │
  ├─────────────────┼──────────────────────────────────────────────────────┤
  │ Intake          │ Cycle opened; client onboarding refreshed.            │
  │ Data Aggregation│ Pull income, deductions, holdings (integration kept). │
  │ Modeling        │ Advisor builds 2–5 scenarios (typed-in figures).      │
  │ Review          │ Firm Admin (quality reviewer) signs off on modeling   │
  │                 │ assumptions, or sends back to the Advisor.            │
  │ Client Approval │ Advisor presents; the cycle awaits the client's       │
  │                 │ approval of N action items.                           │
  │ Executed        │ Approved action items tracked to completion.          │
  │ Archived        │ Firm Admin closes & seals the cycle for compliance.   │
  └─────────────────┴──────────────────────────────────────────────────────┘

  No separate status field. The cycle's condition is fully captured by its
  stage: `Client Approval` is the awaiting-client stage and `Archived` is the
  gated, audited "close & seal" terminal stage. A pause is a boolean `on_hold`
  (+ `hold_reason`) on the case, independent of the workflow position.

Internal roles (firm staff — the tenant):
  • Firm Admin       — Workspace, users, and compliance policy; also acts as
                       quality reviewer: signs off on modeling assumptions and
                       disclosure compliance before the client is presented to,
                       reassigns work, and closes/seals completed cycles. (An
                       Advisor cannot review their own modeling — the Admin is
                       the required second pair of eyes.)
  • Advisor          — Owns the client relationship; aggregates data, builds
                       scenarios, recommends, presents to the client, and
                       tracks action completion.

External roles (the firm's clients):
  • Client           — Individual / self-employed / corporate-officer filer
                       using the portal.

Platform role:
  • Admin            — TaxPulse platform operator (vendor). No impersonation.

Permission Matrix (internal):
  ┌──────────────────────────────┬──────────┬──────────┐
  │ Feature                      │ Firm Admn│ Advisor  │
  ├──────────────────────────────┼──────────┼──────────┤
  │ Case Queue                   │ FULL     │ SCOPED   │
  │ Case Detail                  │ FULL     │ EDIT     │
  │ Data Aggregation Run         │ FULL     │ EDIT     │
  │ Scenario Modeling            │ FULL     │ EDIT     │
  │ Submit for Review            │ FULL     │ EDIT     │
  │ Review Sign-Off / Send Back  │ FULL     │ —        │
  │ Present to Client            │ FULL     │ EDIT     │
  │ Action Item Tracking         │ FULL     │ EDIT     │
  │ Close & Seal (→ Archived)    │ FULL     │ —        │
  │ Client Comms / Scheduling    │ FULL     │ EDIT     │
  │ Audit Trail                  │ FULL     │ VIEW     │
  │ User Management              │ FULL     │ —        │
  └──────────────────────────────┴──────────┴──────────┘

Permission Matrix (external):
  ┌──────────────────────────────┬──────────┐
  │ Feature                      │ Client   │
  ├──────────────────────────────┼──────────┤
  │ Client Portal Dashboard      │ FULL     │

CROSS-CUTTING CAPABILITIES
═══════════════════════════════════════════════════════════════════════════════

  • Multi-tenancy           Each customer firm is a tenant with its own
                            workspace; data is isolated at the database
                            layer. The platform Admin role exists for the
                            vendor but does NOT impersonate into tenants in
                            the MVP.

  • Case lifecycle          Every Case carries: ID, current stage, an
                            `on_hold` pause flag, assigned owner, priority,
                            due date, comments thread, attachments, audit
                            trail, and a stage-transition log. There is no
                            separate status field — condition lives in the
                            stage (see each product's stage table).

  • Due dates (no SLA)      Each case carries a due_date; cases past due show
                            an "Overdue" badge in the queue. No SLA timers,
                            escalation routing, background jobs, or a separate
                            Overdue queue in the MVP.

  • Workflow enforcement    Stage transitions are gated by role + current
                            state, with optional second-pair review modeled
                            as a normal role-gated transition (REVIEW
                            permission). Attempts denied by the engine are
                            recorded in the audit trail.

  • Audit trail             Immutable per-case log of who-did-what-when.
                            Required reading for reviewer roles; visible
                            (read-only) to most others; sealed for archive.

  • Internal vs External UX Internal users see the Case Queue and Case Detail
                            as their primary workspace. External users see a
                            Client / Employee Portal that shows only their own
                            data and the current stage of their Case.

  • Authentication          Email + password WITH MFA for all users (internal
                            and external). No SSO/SAML/OIDC/magic-link in the
                            MVP.

  • Wireframe affordance    The top-bar "View as" role switcher is a
                            design-review aid only. In production, the
                            authenticated user's role + tenant determine both
                            UI and API authorization.
