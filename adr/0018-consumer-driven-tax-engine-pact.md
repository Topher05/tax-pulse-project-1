# ADR-0018: Consumer-driven Pact for the Tax Engine boundary

## Context

The Core Case Service and Tax Calculation Engine are separate bounded contexts. The
Core service owns Tax Plan Cycles and persisted scenario results, while the Tax Engine
owns tax calculation rules and exposes HTTP endpoints for calculation and scenario
comparison.

A shared type or schema can describe the intended shape, but it does not prove the
Core service actually sends that shape or that the Tax Engine keeps returning the
fields the Core service reads. The project owns both services, so the most important
contract is the consumer's real usage of the provider.

## Decision

The Core Case Service to Tax Calculation Engine HTTP boundary uses consumer-driven
Pact testing.

The Core Case Service is the Pact consumer. The Tax Calculation Engine is the Pact
provider. The consumer pact is generated by running the real TypeScript Tax Engine
client against Pact's mock provider, not by hand-writing a standalone contract.

SCRUM-88 records the consumer pact for:

- `POST /tax-calculations`
- `POST /scenarios/comparisons`

The contract includes the request fields the Core service sends and the response fields
the Core service reads for calculation and scenario modeling. Provider verification
against the real FastAPI service is handled by SCRUM-89.

Third-party integrations that TaxPulse does not own should not use Pact unless the
provider can participate in verification. For those integrations, use integration tests,
published provider documentation, and defensive runtime validation instead.

## Consequences

* Breaking Tax Engine changes to fields the Core service reads can be caught by Pact
  provider verification before deploy.
* The provider may add fields the Core service ignores without breaking this consumer
  pact.
* The local generated pact file is the shared contract artifact for the next provider
  verification ticket.
* The Core service must keep the Pact test tied to real client code so the contract
  stays scoped to actual consumer behavior.

## Alternatives considered

* **Producer-driven contract from the Tax Engine.** Rejected for this internal pair
  because it would describe what the provider offers instead of pinning what the Core
  service actually depends on.
* **Only rely on shared schemas.** Rejected because schemas alone do not prove the
  provider returns the fields the consumer reads or that the consumer sends the expected
  request.
* **Pact-test every integration.** Rejected because Pact only pays off when the team can
  verify both sides. Third-party providers should be covered with integration tests and
  defensive validation instead.
